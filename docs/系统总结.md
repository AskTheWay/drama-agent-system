# 短剧 Agent 系统 — 完整技术总结

## 一、系统定位

**短剧投流素材智能剪辑 Agent 系统** — 输入短剧素材（ASR 文本 + 帧描述），通过多 Agent 协作分析、检索、质检、生成，输出结构化剪辑方案。

## 四、LangGraph 工作流详解

### 4.1 状态定义 (WorkflowState)

```python
class WorkflowState(TypedDict):
    # 输入
    asr_text: str                    # ASR 转写文本
    filename: str                    # 文件名
    frame_descriptions: list         # 帧描述列表

    # 节点输出
    analysis: dict                   # 节点1: 视频分析结果
    strategy: dict                   # 节点2: 策略检索结果
    plan: dict                       # 节点3: 剪辑方案
    plan_score: float                # 方案质量分（generate 节点 _calc_quality 计算）

    # 质量控制
    quality_score: float             # 质量检查分（100 分制纯扣分，0-100）
    retry_count: int                 # 当前重试次数
    max_retries: int                 # 最大重试次数

    # 人工介入
    human_feedback: str              # 人工反馈文本
    human_approved: bool             # 是否通过
    need_human_review: bool          # 是否需要人工审核

    # 流程控制
    current_node: str                # 当前节点名
    status: str                      # pending/running/paused/completed

    # 执行日志
    steps: list                      # 每步执行详情
```

### 4.2 节点职责

| 节点 | 职责 | 输入 state 字段 | 输出 state 字段 |
|------|------|----------------|----------------|
| **analyze** | 原视频深度理解 | asr_text, filename, frame_descriptions | analysis |
| **retrieve** | 爆款策略检索 (RAG) | analysis.category, analysis.sub_category, human_feedback（打回时拼入 query） | strategy |
| **quality_check** | 质量检查（100 分制纯扣分） | analysis, strategy | quality_score |
| **retry_increment** | 重试计数+1（留痕到 steps） | retry_count | retry_count |
| **human_review** | 人工审核暂停 | quality_score | status=paused |
| **generate** | 剪辑方案生成（EditPlanSchema 校验） | analysis, strategy, human_feedback | plan, plan_score |

> 每个节点的 steps 记录均带 llm_mode（real/mock），前端据此展示「真实 LLM / 兜底演示数据」徽章。

### 4.3 数据流转

```
analyze 输出 analysis:
  {hook_analysis, emotion_curve, category, sub_category, key_features, beat_points}
       │
       ▼
retrieve 输入 analysis 的 category/sub_category/hook_text，构造 RAG 查询
retrieve 输出 strategy:
  {matched_strategies, strategy_summary, recommended_hook, retrieved_refs}
       │
       ▼
quality_check 输入 analysis + strategy，评分（100 分制纯扣分，零问题 = 100 分直接通过）
  ├── score < 70 且 retry < max → retry_increment → retrieve（回溯）
  ├── score >= 70 或 retry >= max（自动模式）→ generate（跳过人工审核直达）
  └── score >= 70 或 retry >= max（人工介入模式）→ human_review
       │
       ▼
human_review 暂停，等待人工
  ├── approved=true → generate
  ├── approved=false → retrieve（「人工反馈：...」拼入检索 query 回溯）
       │
       ▼
generate 输入 analysis + strategy + human_feedback
generate 输出 plan + plan_score（方案质量分，_calc_quality 计算，与 quality_score 分离）:
  {plan_id, title, segments, beat_points, emotion_curve, estimated_ctr}
```

### 4.4 回溯机制

**回溯复用 vs 覆盖：**
- **保留**: analysis（节点1结果）、steps（执行日志）、retry_count
- **覆盖**: strategy（节点2每次重新检索）
- **累加**: retry_count +1，steps 追加新记录

**run_workflow_with_interrupt 的暂停实现：**
- 通过 `app.stream()` 逐节点迭代，检测到 human_review 节点输出 `status=paused` 后提前返回中间状态
- 并非 LangGraph 原生 interrupt/checkpointer 机制（代码中已加注释说明），恢复时由 resume_workflow 手工调用后续节点

**resume_workflow 不重跑图：**
- 人工审核通过 → 直接调 `node_generate(state)`
- 人工打回 → `retry_count+1` 后直接调 `node_retrieve → node_quality_check → node_generate`

## 六、技术选型对比

### 6.1 Agent 编排：LangGraph vs 纯 LangChain vs 自建

| 维度 | LangGraph | 纯 LangChain Chain | 自建状态机 |
|------|-----------|-------------------|-----------|
| **状态管理** | 节点返回增量 state，框架自动 merge（TypedDict 仅声明字段类型） | 隐式传递 | 手动管理 |
| **条件路由** | add_conditional_edges | 自定义 | if/else |
| **回溯/循环** | 原生支持 | 不支持 | 手动实现 |
| **人工介入** | interrupt/Command | 无原生支持 | 手动实现 |
| **可视化** | 内置 graph 画图 | 无 | 无 |
| **学习成本** | 中等 | 低 | 低 |
| **适合场景** | 多节点有状态工作流 | 简单线性链 | 完全自定义 |

**本系统选择 LangGraph 的原因：**
- 需要回溯重试（quality_check → retrieve 循环）
- 需要人工审核暂停/恢复
- 需要状态在节点间显式传递

> 注：人工介入未使用 LangGraph 原生 interrupt/Command + checkpointer，而是 `app.stream()` 迭代 + 检测 paused 提前返回的实现（见 4.4），属于学习项目的简化取舍。

### 6.2 向量检索：FAISS vs Elasticsearch vs Pinecone

| 维度 | FAISS | Elasticsearch | Pinecone |
|------|-------|---------------|----------|
| **部署** | 嵌入式，零依赖 | 需独立服务 | SaaS |
| **全文搜索** | ❌ 不支持 | ✅ 原生支持 | ❌ 不支持 |
| **结构化过滤** | Python 内存过滤 | 原生 filter | 原生 filter |
| **向量检索** | ✅ 高性能 | ✅ KNN | ✅ 高性能 |
| **CRUD** | 仅追加 | 完整支持 | 完整支持 |
| **数据量** | 百万级 | 千万级 | 十亿级 |
| **混合查询** | 需手动组合 | 一次查询搞定 | 一次查询搞定 |
| **成本** | 免费 | 免费（自部署） | 付费 |

**本系统选择 FAISS 的原因：**
- 数据量极小（6 条），暴力搜索毫秒级
- 零依赖，嵌入式部署
- 配合 SQLite 元数据过滤，够用

**如果数据量增长到万级以上，应迁移到 ES。**

### 6.3 数据库：SQLite vs PostgreSQL vs MongoDB

| 维度 | SQLite | PostgreSQL | MongoDB |
|------|--------|-----------|---------|
| **部署** | 单文件 | 需独立服务 | 需独立服务 |
| **并发** | 单写多读 | 高并发 | 高并发 |
| **JSON 支持** | JSON 列 | JSONB | 原生文档 |
| **事务** | ✅ | ✅ | ✅ |
| **ORM** | SQLAlchemy | SQLAlchemy | ODM |
| **适合场景** | 原型/单机 | 生产环境 | 灵活 schema |

**本系统选择 SQLite 的原因：**
- 原型阶段，单机部署
- 数据量小，无并发需求
- 零配置，文件即数据库

### 6.4 LLM 调用：LangChain vs 原生 SDK

| 维度 | LangChain ChatOpenAI | 原生 httpx/requests |
|------|---------------------|--------------------|
| **结构化输出** | JsonOutputParser 自动解析 | 手动解析 |
| **Prompt 模板** | ChatPromptTemplate | 手动拼接 |
| **多模型切换** | 换一行代码 | 改 API 地址 |
| **调试** | LangSmith 集成 | 手动日志 |
| **依赖** | 重（整个 LangChain） | 轻 |

**本系统选择 LangChain 的原因：**
- JsonOutputParser 强制 LLM 输出合法 JSON
- PromptTemplate 可复用
- 已经用了 LangGraph，顺带用 LangChain

## 九、核心设计模式

### 9.1 数据飞轮

```
投流效果 → feedback API → 更新 DB HotRef.score → VectorStore.update_scores() → 影响下次检索排序
 (CTR/留存)  (score 校验0-100,   (加权移动平均       (同步内存元数据并落盘)      (高分素材优先被召回)
              plan 不存在404)     0.8旧+0.2新)
```

> 闭环关键：feedback 更新 DB 后会同步调用 `VectorStore.update_scores()` 刷新检索元数据并落盘，否则 DB 分数变了而检索排序仍用旧元数据，「高分策略优先被召回」不会真正生效。

### 9.2 双模 RAG

```
元数据预过滤（硬规则）: category/sub_category 精确匹配（无匹配时回退全量候选集并 log warning）
       +
语义向量检索（软匹配）: FAISS 余弦相似度 top-k
       ↓
按业务分数排序（数据飞轮权重）
```

### 9.3 质量门控 + 回溯

```
quality_check 评分（100 分制纯扣分，零问题 = 100 分直接通过）
  score < 70 且 retry < max_retries(2) → retry_increment → retrieve 重新检索
  达标或重试耗尽时：自动模式直达 generate（跳过人工审核）；
                   人工介入模式暂停在 human_review
  人工可打回并附带反馈，retrieve 会将「人工反馈：...」拼入检索 query
```
