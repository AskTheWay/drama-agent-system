# 日志系统详解 — 当前实现与局限

## 一、当前日志架构

本系统有 **两套日志机制**，都没有使用专业日志框架：

```
┌─────────────────────────────────────────────────────────┐
│                    日志分层                               │
├─────────────────────────────────────────────────────────┤
│  1. 控制台 print()     →  运行时调试日志（不持久化）       │
│  2. _record_step()     →  工作流执行步骤（内存中，API返回） │
│  3. SQLite 数据库      →  业务结果数据（持久化）           │
└─────────────────────────────────────────────────────────┘
```

---

## 二、print() 日志 — 纯控制台输出

### 2.1 使用方式

```python
# agent_workflow.py
print("[节点1] 原视频深度理解...")
print(f"[节点1] 完成，赛道={category}/{sub_category}")
print(f"[质量检查] 得分={score}, 问题={issues}, 重试次数={retry_count}")

# vector_store.py
print(f"[向量库] 已加载 {self.index.ntotal} 条向量")
print(f"[警告] Embedding API 失败: {e}，使用随机向量")

# main.py — 无 print，依赖 uvicorn 自带日志
```

### 2.2 特点

| 项目 | 说明 |
|------|------|
| 框架 | 无，原生 `print()` |
| 输出 | 仅 stdout（控制台） |
| 持久化 | ❌ 不持久化，关窗口就没了 |
| 级别 | 无级别区分（info/warning/error 混在一起） |
| 格式 | 手动拼接 `[前缀] 内容` |
| 时间戳 | 无 |
| 结构化 | 无 |

### 2.3 问题

```python
# 当前：手动加前缀，无统一格式
print("[节点1] 完成")           # info 级别
print(f"[警告] API 失败: {e}")  # warning 级别
# 没有 error/critical 级别
# 没有时间戳
# 没有文件/行号信息
```

## 三、_record_step() — 工作流执行步骤记录

### 3.1 实现原理

```python
# agent_workflow.py:67-79
def _record_step(state: WorkflowState, node: str, desc: str,
                 input_summary: dict, output_summary: dict, duration_ms: float) -> list:
    """记录一个节点的执行详情"""
    steps = list(state.get("steps") or [])
    steps.append({
        "node": node,           # 节点名: analyze/retrieve/quality_check/...
        "desc": desc,           # 中文描述
        "input": input_summary, # 输入摘要 dict
        "output": output_summary,# 输出摘要 dict
        "duration_ms": round(duration_ms, 0),  # 耗时毫秒
        "timestamp": datetime.now().strftime("%H:%M:%S"),  # 时间戳
    })
    return steps
```

### 3.2 数据流

```
节点执行
  │
  ├─ 记录开始时间 t0
  │
  ├─ 执行业务逻辑
  │
  ├─ 计算 duration = (time.time() - t0) * 1000
  │
  ├─ 调用 _record_step(state, "节点名", "描述", input_dict, output_dict, duration)
  │     │
  │     └─ 追加到 state["steps"] 列表
  │
  └─ 返回 {**state, "steps": steps}
        │
        └─ LangGraph 传递给下一个节点
              │
              └─ 最终通过 API 返回给前端
```

### 3.3 存储位置

```
steps 数据的生命周期:

1. 内存中: state["steps"] = [...]
   - 在 LangGraph 节点间传递
   - 每个节点追加一条记录

2. API 响应: {"steps": [...], "analysis": {...}, ...}
   - 通过 /api/analyze 等接口返回

3. 前端渲染: renderSteps(data.steps)
   - 显示在页面上

4. ❌ 不持久化到数据库
   - 关闭页面后丢失
   - 无法回溯历史执行记录
```

## 五、对比：当前 vs 专业方案

| 维度 | 当前实现 | Python logging | ELK Stack |
|------|---------|---------------|-----------|
| 框架 | print() | logging 标准库 | Filebeat + ES + Kibana |
| 级别 | 无 | DEBUG/INFO/WARNING/ERROR | 同 |
| 时间戳 | 手动 %H:%M:%S | 自动，毫秒精度 | 自动，ISO 8601 |
| 输出目标 | stdout | stdout/文件/远程 | 文件 → ES → Kibana |
| 持久化 | ❌ | ✅ 文件轮转 | ✅ 集中存储 |
| 结构化 | dict 手动拼 | Formatter 自定义 | JSON 自动解析 |
| 检索能力 | ❌ | grep 文件 | Kibana 全文检索 |
| 依赖 | 无 | 无（标准库） | 需部署 ES + Kibana |

## 六、如果要改进

### 6.1 最小改动：用 logging 替换 print

```python
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s [%(levelname)s] %(message)s",
    handlers=[
        logging.StreamHandler(),                    # 控制台
        logging.FileHandler("data/app.log", encoding="utf-8"),  # 文件
    ]
)
logger = logging.getLogger(__name__)

# 替换 print
logger.info("[节点1] 完成，赛道=%s/%s", category, sub_category)
```

## 七、总结

```
当前系统的"日志"其实是三层东西混在一起：

1. print()        → 开发调试用，不持久化，不结构化
2. _record_step() → 工作流透明度用，内存中传递，API返回前端展示
3. SQLite         → 业务数据持久化，但不含执行日志

没有使用任何日志框架（logging/loguru/structlog）。
没有日志持久化。
没有集中式日志收集（ELK/Loki）。
```
