# 日志系统详解 — 当前实现与局限

## 一、当前日志架构

本系统使用 Python logging 标准库做运行日志（`logger.py` 统一配置），另有两条「类日志」通道：

```
┌─────────────────────────────────────────────────────────┐
│                    日志分层                               │
├─────────────────────────────────────────────────────────┤
│  1. logging 标准库      →  运行日志（控制台 + data/app.log）│
│     └─ flow_logger     →  节点间数据流转（data/flow.log）  │
│  2. _record_step()     →  工作流执行步骤（内存中，API返回） │
│  3. SQLite 数据库      →  业务结果数据（持久化）           │
└─────────────────────────────────────────────────────────┘
```

## 二、logging 标准库日志 — logger.py 统一配置

### 2.1 统一配置（logger.py）

```python
# logger.py — 进程内首次 import 该模块时触发 basicConfig
import logging, os

LOG_DIR = os.path.join(os.path.dirname(__file__), "data")
os.makedirs(LOG_DIR, exist_ok=True)

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s [%(levelname)s] %(name)s - %(message)s",
    datefmt="%Y-%m-%d %H:%M:%S",
    handlers=[
        logging.StreamHandler(),                                  # 控制台
        logging.FileHandler(os.path.join(LOG_DIR, "app.log"),     # 文件持久化
                            encoding="utf-8"),
    ],
)

def get_logger(name: str) -> logging.Logger:
    return logging.getLogger(name)
```

各模块统一通过 `get_logger(__name__)` 获取 logger 实例（agent_workflow.py / vector_store.py / video_processor.py / mock_data.py），logger 名即模块名，天然形成层级。

### 2.2 使用方式（当前真实调用）

```python
# agent_workflow.py — node_analyze
logger.info("[节点1] 原视频深度理解...")
logger.info(f"[节点1] 完成，赛道={category}/{sub_category}")
logger.warning(f"[节点1] LLM 失败，使用模拟: {e}")
logger.info(f"[质量检查] 得分={score}, 问题={issues}, 重试次数={retry_count}")

# vector_store.py
logger.info(f"已加载 {self.index.ntotal} 条向量")
logger.warning(f"Embedding API 失败: {e}，使用随机向量降级（索引不持久化）")
logger.warning(f"元数据预过滤无匹配（category={category}, sub_category={sub_category}），"
               "回退全量候选集——注意此时返回结果可能与请求赛道不符")

# main.py — 无直接日志调用，依赖 uvicorn 自带日志
```

### 2.3 特点

| 项目 | 说明 |
|------|------|
| 框架 | Python logging 标准库（logger.py 统一 basicConfig） |
| 输出 | 控制台 + data/app.log 双写（双 handler） |
| 持久化 | ✅ app.log 文件（但无轮转） |
| 级别 | INFO / WARNING / ERROR 区分（flow_logger 另用 DEBUG） |
| 格式 | 统一 Formatter：`时间 [级别] 模块名 - 消息` |
| 时间戳 | ✅ 自动（%Y-%m-%d %H:%M:%S） |
| 结构化 | ❌ 纯文本；仅 flow.log 为单行 JSON（见 2.5） |

### 2.4 问题

```python
# 现存局限：
# - app.log 无轮转（RotatingFileHandler），长期运行会无限增长
# - 纯文本格式，机器解析不便（无 JSON 结构化日志）
# - 无集中式收集，多副本/容器部署时日志分散在各处
# - print() 时代的问题（无级别/无时间戳/不持久化）已随 logger.py 落地解决
```

### 2.5 数据流转专用 logger — flow_logger

`logger.py` 额外定义了一个专用通道，把每个节点执行后的完整 state 写入 `data/flow.log`，便于事后回放排查：

```python
# logger.py
flow_logger = logging.getLogger("flow")
flow_logger.setLevel(logging.DEBUG)
flow_logger.propagate = False  # 防止 DEBUG 级完整 state 冒泡到 root logger 重复输出
_flow_handler = logging.FileHandler(
    os.path.join(LOG_DIR, "flow.log"), encoding="utf-8"
)
_flow_handler.setFormatter(logging.Formatter(
    "%(asctime)s %(message)s", datefmt="%H:%M:%S"
))
flow_logger.addHandler(_flow_handler)
```

**`propagate = False` 是这里的关键设计**：logging 的日志事件默认会沿层级向 root logger 冒泡，由 root 的 handler 再输出一遍。flow_logger 记录的是 DEBUG 级完整 state（体积大），若不关闭冒泡，这些内容会重复出现在控制台和 app.log 里，形成噪音。关闭后 flow.log 成为独立通道：完整数据只进专属文件，控制台/app.log 只保留 INFO 级业务日志。

写入侧在 agent_workflow.py 的 `_log_flow()` 中，每个节点结束时调用：

```python
# agent_workflow.py — _log_flow()
def _log_flow(node: str, state: dict):
    """记录节点间数据流转"""
    logger.info(f"[数据流转] {node} → {_build_schema(state)}")   # 摘要 → 控制台/app.log
    flow_data = {k: _truncate_val(k, v) for k, v in state.items()}
    flow_logger.debug(f"[{node}] {json.dumps(flow_data, ensure_ascii=False, default=str)}")  # 完整 → flow.log
```

注意 `_truncate_val` 会截断超长字段（如超过 500 字的文本），flow.log 记录的是「截断后的完整 state」，既保信息量又防单行爆炸。

## 三、_record_step() — 工作流执行步骤记录

### 3.1 实现原理

```python
# agent_workflow.py — _record_step()
def _record_step(state: WorkflowState, node: str, desc: str,
                 input_summary: dict, output_summary: dict, duration_ms: float) -> list:
    """记录一个节点的执行详情"""
    steps = list(state.get("steps") or [])
    steps.append({
        "node": node,           # 节点名: analyze/retrieve/quality_check/...
        "desc": desc,           # 中文描述
        "input": input_summary, # 输入摘要 dict
        "output": output_summary,# 输出摘要 dict
        "duration_ms": round(duration_ms, 0),  # 耗时毫秒
        "timestamp": datetime.now().strftime("%H:%M:%S"),  # 时间戳
    })
    return steps
```

两个补充说明（当前代码行为）：

- 各节点调用 `_record_step` 时会把 `llm_mode`（real/mock）放进 output_summary，前端据此显示「真实 LLM / 兜底演示数据」徽章；
- 回溯重试时 `node_retry_increment()` 也会调用 `_record_step` 留痕（node="retry_increment"），所以质量检查未达标 → 重试的轨迹在 steps 里可见。

### 3.2 数据流

```
节点执行
  │
  ├─ 记录开始时间 t0
  │
  ├─ 执行业务逻辑
  │
  ├─ 计算 duration = (time.time() - t0) * 1000
  │
  ├─ 调用 _record_step(state, "节点名", "描述", input_dict, output_dict, duration)
  │     │
  │     └─ 追加到 state["steps"] 列表
  │
  └─ 返回 {**state, "steps": steps}
        │
        └─ LangGraph 传递给下一个节点
              │
              └─ 最终通过 API 返回给前端
```

### 3.3 存储位置

```
steps 数据的生命周期:

1. 内存中: state["steps"] = [...]
   - 在 LangGraph 节点间传递
   - 每个节点追加一条记录

2. API 响应: {"steps": [...], "analysis": {...}, ...}
   - 通过 /api/analyze 等接口返回

3. 前端渲染: renderSteps(data.steps)
   - 显示在页面上

4. ❌ 不持久化到数据库
   - 关闭页面后丢失
   - 无法回溯历史执行记录
```

## 五、对比：当前 vs 专业方案

| 维度 | 当前实现 | logging 进阶用法 | ELK Stack |
|------|---------|---------------|-----------|
| 框架 | logging 标准库（logger.py） | logging + 扩展 | Filebeat + ES + Kibana |
| 级别 | INFO/WARNING/ERROR（flow: DEBUG） | 同 + 自定义级别/过滤器 | 同 |
| 时间戳 | 自动，秒级（datefmt） | 自动，毫秒精度 | 自动，ISO 8601 |

| 依赖 | 无（标准库） | 无/轻量 | 需部署 ES + Kibana |

## 七、总结

```
当前系统的"日志"是四层东西：

1. logging 标准库  → 运行日志，控制台 + data/app.log 持久化（logger.py 统一配置）
2. flow_logger    → 节点间数据流转，DEBUG 级完整 state 写 data/flow.log
                    （propagate=False 独立通道，不污染 app.log）
3. _record_step() → 工作流透明度用，内存中传递，API返回前端展示
                    （含 llm_mode 徽章数据、回溯重试留痕）
4. SQLite         → 业务数据持久化，但不含执行日志

已具备：logging 标准库框架、级别区分、统一格式、文件持久化。
仍欠缺：日志轮转、JSON 结构化、集中式日志收集（ELK/Loki）、steps 历史持久化。
```
